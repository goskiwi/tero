# RepoMap 本地定位对照

2026-09-09。没有调用 LLM。使用前一轮已经标注的 6 个跨文件定位任务与同一份 Tero 源码快照，结果出炉后没有调整问题、答案或权重。

对照为同一 Tree-sitter 符号集合上的关键词评分，实验组为现有 RepoMap（关键词＋图排序）。两组使用相同类型加分、文件多样性选择、最多 24 个符号和 1,200-token 渲染预算。这里不是与 grep 比较，也不测 Agent 完整任务成功率。

文件指标：实际地图输出中前 5 个不同文件，对预先标注的必要文件计算召回。符号指标：必要函数是否出现在实际渲染输出中，不能只出现在内部排名中。分母按任务累计，同一文件在不同任务中分别计数。

| 指标 | 仅关键词 | 完整 RepoMap |
| --- | ---: | ---: |
| 必要文件召回@5 | 8/15（53.3%） | 8/15（53.3%） |
| 必要符号覆盖 | 8/16（50.0%） | 11/16（68.8%） |
| 首次构建中位耗时 | 33.55 ms | 33.52 ms |
| 缓存后查询＋渲染中位耗时 | 2.41 ms | 5.76 ms |

| 任务 | 关键词符号命中 | RepoMap 符号命中 |
| --- | ---: | ---: |
| 压缩链路 | 0/3 | 2/3 |
| 中断恢复 | 1/2 | 1/2 |
| 完成验证 | 3/3 | 3/3 |
| 并行读取 | 1/3 | 1/3 |
| 文件修改与 Diff | 1/2 | 1/2 |
| 超时取消 | 2/3 | 3/3 |

这批样本中，完整 RepoMap 多覆盖 3 个必要符号，提升 18.75 个百分点；前五文件召回没有改善。收益来自压缩与超时两项任务，不能描述为所有任务都有提升，也不能推导模型 Token 节省。

每个任务用新对象测一次构建，查询＋渲染重复 7 次取中位数，再汇总任务中位数。操作系统缓存未控制，因此首次构建不是冷磁盘性能。关键词组为了控制候选集合也复用建图过程，其构建耗时不代表一个独立 grep 工具的成本。

局限：一个小型 Python 仓库，6 个人工选择的任务；符号覆盖仍有 5/16 未命中。前一轮开放式 Agent 实验已中止，不将其中不完整结果与本轮混合。

原始结果、每组实际地图、协议及源码快照：`benchmarks/results/repomap-local-20260909/`。脚本：`evaluations/repomap_local.py`。

复现（不需要 API key）：

```sh
python -m evaluations.repomap_local --source-run .tero/experiments/repomap-ab-20260909 --output /tmp/tero-repomap-new-results
```

若原实验目录不可用，可新建目录，将结果中的 `source.zip` 解压为该目录的 `source/`，并将结果中的 `protocol.json` 复制到目录根，再将该目录传给 `--source-run`。
