正常组完成订单、库存、重复请求、取消、存储、CLI 和文档，原始 25 个 unittest 用例通过，测试与 AGENTS.md 未改。单次最大实际输入为 47,319 token，没有自然压缩。

压缩组第 3 轮后实际进入摘要生成，但摘要未通过完整性／长度校验，任务停止，独立验收失败。不是压缩后完成。压缩提交次数为 0，摘要覆盖位置仍为 0，原始历史和需求未删除。

压缩组逐请求的原始需求保留、工具调用与结果配对检查全部通过。但摘要错误目前合并了空内容、超长、缺段三种原因，无法从已保存日志确定本次具体是哪一种；不能凭输出 Token 推断正文长度。

结论：一次较长开发任务通过，不代表上下文管理通过。本次真实压缩专项失败，后续应先细分摘要校验诊断，并对同一历史进行摘要生成／校验复测；不通过删除约束、截断摘要或增大触发阈值掩盖失败。

正常组证据：`.tero/evaluations/long-orders/evaluation.json`；压缩组证据：`.tero/evaluations/long-orders-compressed/evaluation.json`。包含独立验收输出、Session 和 Trace。

新增提前压缩阈值与工具配对／原始需求保留回归后，本地测试 58 passed。此处不宣称统计性能收益，也没有完整 1M 输入压力测试。

## 同一失败历史的摘要复现

单独重放摘要生成，不重跑订单任务、不修改原 Session。复现返回 `summary` 字符串，估算 2,162 token，六个标题齐全，低于 4,096 正文预算，校验通过。诊断在 `.tero/evaluations/summary-diagnosis/`。

原失败请求正常完成，usage 显示总输出 17,347，其中推理 17,005，因此不同于之前的输出额度耗尽。原候选正文未持久化，不能准确恢复是哪一项校验不符。相同历史的再次生成通过说明本次复现未稳定重现错误，不证明原问题已修复。确定的工程问题是：仅用 JSON object 模式，字符串字段及 Markdown 标题靠提示词；校验原因未细分；提前压缩失败即结束整个任务，未区分仍有硬窗口空间的情形。
